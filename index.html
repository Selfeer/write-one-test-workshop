01

What is ClickHouse?

And why is it so fast at analytics?

Section 1: about 8 minutes. The goal is not to sell ClickHouse. It's for people to understand enough of its design to see why testing it is hard.
ClickHouse in one slide

An open-source, column-oriented SQL database for analytics

Transactional (OLTP)

SELECT * FROM orders
WHERE id = 42

Finds one row fast. Many small reads and writes.

PostgreSQL, MySQL

Analytical (OLAP)

SELECT country, avg(price)
FROM orders GROUP BY country

Reads billions of rows, but only a few columns.

ClickHouse, BigQuery, Snowflake

Used for logs, metrics, events and clickstreams: data that is written once and read for totals and averages.

Keep it concrete: "Your bank's app showing your balance is OLTP. The bank's report on average spending per country is OLAP." ClickHouse is built for the second kind of question.
Why columnar is fast · 1

Read only what the query needs

SELECT avg(price) FROM sales WHERE country = 'DE'

Row store: whole rows, one after another

read 0 of 40 values

Column store: each column is its own file

read 0 of 40 values
1 billion rows × 100 columns, and the query uses 2 of them: a column store reads 2% of the data.
Key slide. Step 1: a row store has to read every row whole, even the columns we don't use. Step 2: a column store opens only the country and price files. Step 3: at real scale that's reading 2% of the disk instead of 100%.
Why columnar is fast · 2

Similar values next to each other compress well

The country column, sorted by the table's key

The timestamp column: store the difference, not the value

Then a general compressor (LZ4, ZSTD) on top

raw
stored

Smaller files mean less to read from disk, and reading from disk is usually the slowest part.

Step 1: run-length encoding, "DE five times". Step 2: delta encoding, so each timestamp becomes a small number. Step 3: a general compressor on top. Ratios depend on the data. Several times smaller is common for this kind of data, but don't promise a number.
Why columnar is fast · 3

Skip whole blocks you don't need

SELECT count() FROM events WHERE date BETWEEN '2024-06-01' AND '2024-06-30'

Data is sorted by the key and split into granules of 8,192 rows. A small index stores the first key of each granule.

The index shows only 2 granules can match, so ClickHouse reads 16,384 rows instead of 131,072.

This is the sparse primary index. It's tiny, so it stays in memory, and it lets ClickHouse skip most of the table.
Why columnar is fast · 4

Use every core, then every server

Every CPU core works on a block of values

core 3

Click: → the query goes out, ← partial results come back and are merged.

Shards split the data, replicas copy it

Left: each core works on a block of column values at a time, so the CPU stays busy. Right, click through: the query fans out to one replica of each shard, each shard computes a partial result, and the first node merges them.
Bridge: "Great for speed. Now count the moving parts: shards, replicas, background merges, copying between replicas, a coordination service. That's what makes it hard to test."
02

What do we test, and why?

Section 2: about 7 minutes.
The question we ask

Not "is it fast?" but "is it right, in every situation?"

Performance testing

  • A few tuned queries
  • Measures time
  • "25% faster than last release"

Functional regression testing

  • Every feature, under many conditions
  • Checks the result, the error, and the state afterwards
  • "Still correct after an ALTER, during a merge, with a replica down"

A fast wrong answer is worse than a slow right one, because nobody notices it.

This is the mindset shift. We don't look for the best query. We look for the situation the developer didn't think of.

Where bugs hide

Bugs live where features meet

Data: types, edge values, NULLs, file formats, sizes

Operations: INSERT, ALTER, merges, DELETE, SELECT, export

Conditions: settings, order, concurrency, restarts, network faults

Each feature passes its own tests. The bug only shows up when one value meets one operation under one condition.
Swap in one or two real bugs from your own work here. A real story is the part people remember. Typical shape: "a Nullable column, exported to Parquet, while a merge is running on another replica."
The "different situations"

What can vary in a database test?

Data

Int8 … UInt256, Float, Decimal, String, Nullable, Array, Map, JSON. Min, max, 0, −1, NaN, empty.

Schema

Table engines, partition keys, sort keys, codecs, TTL, projections, indexes.

Operations

INSERT, ALTER (add, drop, rename, update), DELETE, merges, moves, attach, detach.

Order & concurrency

Which operation comes first? Which ones overlap? Which one wins?

Configuration

Hundreds of settings, server versions, user privileges, storage policies.

Environment

Cluster layout, a replica down, network delay, a full disk, S3 or local disk.

Each card is a list of variables. Each variable has a list of values. That's all combinatorics needs.

Ask the room: "What else could vary?" Take two or three answers. This is how we start a new suite: write the variables on a board.

The catch

Combinations grow exponentially

variables5 values each (log scale)combinationsat 1 test / second

We can't run everything. The skill is choosing which combinations to run.

Click through the rows. 12 variables with 5 values each is 244 million tests: almost 8 years at one test per second. A real database has far more than 12 variables.
Keeping it under control

Four ways to choose combinations

1 · Pick the values well

Group values that behave the same and keep one from each group, plus the edges: min, max, 0, −1, NaN, empty, NULL.

2 · Pairs instead of everything

Cover every pair of values at least once. Far fewer tests, and most bugs need only two factors.

3 · Random sample, fixed seed

random.seed(42)
random.sample(all, 3000)
Different subsets, but any run can be replayed.

4 · Go big on demand

A small sample on every build. The full set with --stress before a release.

All four are used in the suite. #3 and #4 are in the rbac "simple combinatorics" test we'll see later: 446,865 possible sequences, 3,000 sampled per run, all of them with --stress.
Pairwise testing

81 combinations, or 9 that cover every pair

type: Int, String, Nullable
engine: MergeTree, Replicated, S3
format: Native, Parquet, CSV
setting: on, off, default

All of them: 3⁴ = 81 tests

Pairwise: 9 tests

 

NIST studies of real software (Kuhn et al.) found that most failures were triggered by 1 or 2 factors, and none needed more than 6.

Step 3 is the proof: pick any two columns, for example type × engine. As the highlight walks down the 9 rows, each row fills one cell of the 3 × 3 grid on the right. After 9 rows all 9 pairs are covered, for every pair of columns. That's 11% of the tests and still every two-factor bug. TestFlows has this built in (CoveringArray in testflows.combinatorics); PICT is another tool for it.

And sometimes…

The oracle is wrong, not the database. You'll see that in a minute.

Real bugs we found

Same file, two readers: they must agree

ClickHouse 25.8 got a new, faster Parquet reader behind one setting. We read every test file with the old reader and the new one, and compared.

new reader v3setting = 1
Segmentation fault: the server crashed

Two of the five bugs we filed in two days (22–23 Sep 2025, ClickHouse 25.8.4) when we turned the new reader on. Step 1, #87412: run the same SELECT on the same file again and again; the old reader always gives the same Bool values, the new one gives different ones each run. Fixed in PR #87442; the maintainer first thought it was already fixed. Step 2, #87509: one particular file, a Bool column with a bloom filter in a gzip file, crashes the whole server with a segmentation fault. Step 3: nobody wrote a test for "Bool + bloom filter + gzip + new reader". The test was "every file, both readers, compare". The other three: a type change for Decimal and for DateTime64, and an error reading back a file ClickHouse wrote itself. Links in workshop/BUG_STORIES.md.

What does this return?

ClickHouse widens the type when adding: UInt8 + UInt8 gives UInt16.
One test, one fact. Does it hold for every type?

Most people guess 44 (wrap-around) or an error. It's 300, because ClickHouse widens small integer types. The obvious next question, "does that hold for every type?", is where one test becomes many.

3 of 9 rows fail. UInt64 doesn't widen; max + 1 wraps around to 0.

Is that a bug? Who decides?

It's documented behaviour, so the oracle was wrong. The spec decides what "correct" means, not the test.

Exercise 1 suggested "adding widens the type". The combination with the largest type breaks that rule, and only the max value meeting the max type shows it. In the real suite we'd mark this as expected behaviour and keep the test, so we notice if it ever changes.
Exercise 4 · when "equal" gets hard

Floats: what does "equal" mean?

SELECT a, b, a + b AS ch,
       ch = ch AS equals_itself
FROM values('a Float64', -inf, nan, -0., 0.1, inf) AS A,

inf + -inf is nan, and 0.1 + 0.2 isn't exactly 0.3.

nan = nan is false. An oracle that uses = marks correct results as failures.

That's why plus.py compares str(float(…)): the test needs its own definition of "same".

This is IEEE 754 floating point, not a ClickHouse quirk. The table shows 4 of the 25 rows. Special values (NaN, −0, inf) break naive checks, so the oracle needs special cases, just like the database does.
Exercise 5 · find the crash

One bad combination ruins the whole batch

SELECT a, b, intDiv(a, b) AS result
FROM values('a Int64', -9223372036854775808, 0, 7) AS A,
     values('b Int64', -1, 2) AS B

Code: 153. DB::Exception: Division of minimal signed number by minus one

The smallest Int64 divided by −1 doesn't fit in Int64. One case out of six, and you get no rows at all.

Try it: remove values until the query works. That's finding the culprit by hand.

The fix: run every combination as its own test. One fails, 1,088 still report. The framework does that for us.

This is why we need a framework. In SQL the whole query fails; in TestFlows each combination is a separate scenario with its own name, result and log. Good bridge into the demo.

The real thing

One test from the suite, and how it becomes 1,089

Section 5: about 10 minutes. Start the run now, before you talk through the code, so the output is ready when you switch to the terminal.
functions/tests/plus.py
@TestSketch(Scenario)
def floats(self, client=None):
    """Check addition of floats using plus()"""
    sign = ["-", "+", ""]
    value = ["inf", "nan", "0.0", "0.1", ... 11 values]

    a = either(*sign, i="sign") + either(*value, i="value")
    b = either(*sign, i="sign") + either(*value, i="value")

    expected = float(a) + float(b)
    r = client.query(f"SELECT {a} + {b}").output
    assert str(float(r[0][0])) == str(expected)
@TestSketch: write the test once. The framework runs it for every combination.
either() marks a variable, like the chips on slide 17. Each run takes one of its values.
The oracle: Python computes the expected answer, like expected in exercise 3.
The check: compared as strings, so nan equals nan (exercise 4).
About 10 lines → 1,089 tests, each with its own name, pass/fail and log (exercise 5).
Lines are trimmed slightly to fit; the file is about 30 lines. Tie each part back to the exercises: either() is the values() list, expected is the oracle column, str(float()) handles nan, and separate scenarios fix the "one crash kills everything" problem.

Take this home

The recipe

  1. Write one test that works for one case.
  2. Find its variables: data, schema, operations, order, configuration, environment.
  3. Pick the values: one from each group, plus every edge case.
  4. Combine them: every combination, pairs, or a seeded sample.
  5. Decide the oracle before you trust a single result.
  6. Run in parallel, repeat, add faults, and keep the seed so you can replay.
Nothing here is specific to ClickHouse. The same recipe works for an API, a form, a compiler or a payment flow.
